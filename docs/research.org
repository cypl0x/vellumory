* Rendering pipeline
** Measured: where time goes
- Emacs decode cost on the main thread (forced via =image-size=, flushed
  between runs, pgtk/cairo):

  | image                 | PNG      | PPM (pbm) |
  |-----------------------+----------+-----------|
  | strip 1240×192        | 2.5 ms   | 1.3 ms    |
  | page 1240×1754        | 16–17 ms | 8–10 ms   |
  | page 2480×3508 (2× DPI)| 77 ms    | 51–55 ms  |

- Worker cost: =mutool draw -s t= at 1240 px, 12 pages. PNG encoding dominates:
  minaret 9 ms/page raw vs 50 ms/page PNG; Turm 14 vs 52 ms; monograph pages
  reach 447 ms raw (heavy content), where parallel bands and cancellation matter.
- Opening (old path, every page loaded): 70–80 ms for 240–327 pages. The
  new path reads page boxes from the page tree only.
- Decision: raw binary PPM written to a per-worker tmpfs directory
  (=$XDG_RUNTIME_DIR=), referenced by path. Zero encoding, fastest available
  Emacs decoder, no Lisp string concatenation of pixel data in a process filter.

** MuPDF threading and cancellation
- [[https://mupdf.readthedocs.io/en/latest/reference/c/overview.html][MuPDF overview]] (=docs/reference/c/overview.md:162-307=): one cloned
  context per thread (=fz_clone_context=, =context.h:350-365=), shared
  =fz_locks_context=; only one thread may use a document at a time; a display
  list may be rendered from several threads simultaneously ("banded rendering").
- =fz_cookie= (=device.h:439-486=): unsynchronized; abort may be set from
  another thread, no upper bound on latency, never reset → fresh cookie per job.
- Abort leaves partial pixmaps; =fz_run_display_list= breaks silently
  (=list-device.c:1754=); an aborted =fz_run_page= truncates the recorded list
  (=pdf-interpret.c:1555=) → never cache lists built under an aborted cookie.
- Scissor culling makes strip cost proportional to strip content
  (=list-device.c:1891-1921=), but only with a cached display list.
- Implemented accordingly in =native/mupdf.c=: base context with pthread
  locks, pooled clones, =doc_lock= around all document access, shared LRU of
  24 display lists, aborted builds never published.

** How other viewers render
- PDF.js (279175b): visible pages first, then detail views, then one page in
  scroll direction (=web/pdf_rendering_queue.js:112-188=); =maxCanvasPixels=
  2^25; detail canvas = visible + one viewport each side, skipped during fast
  scrolling (=pdf_viewer.js:2166-2190=); zoom shows CSS-scaled canvas and
  waits 400 ms.
- Chromium PDFium: progressive paint of dirty rects, 250/300 ms pause timeout;
  scrolling reuses painted pixels (=paint_aggregator.cc=).
- Okular: tiles only above 4× screen pixels; 4×4 grid, split tiles > 2 Mpx;
  512 px prefetch margin; aborts a running render on higher priority.
- Evince: 50 MB cache, ±3 pages preload, cancellation only after render.
- zathura: one render thread, generation counter, 16-page cache, scaled
  thumbnail while re-rendering.
- Sioyek: 4 threads with cloned contexts, optional 5-band slicing.
- mupdf-gl: whole page, no display list, no threads.
- Adopted: visible tiles first ordered from a reading focus line, previews
  during fast motion, generation counter, cancellation via cookies, one
  viewport prefetch ahead and half behind, tiles only beyond the window width.

** Emacs image internals (emacs-31 b5c91b3 and master)
- Cache key =sxhash(filter_image_spec(spec))= (=image.c:3545=), O(1) for
  strings; candidates compared with =Fequal= — identical spec objects are
  fastest, so reuse spec objects.
- Decoding is eager in =lookup_image= (=image.c:3568=): =image-size= predecodes.
- =image-flush= → =uncache_image= → =SET_FRAME_GARBAGED= per image
  (=image.c:2293-2312=): flushing is expensive; batch it.
- Automatic eviction every 101 redisplays; above 40 cached images the delay
  shrinks to 1600·300/n² s and any eviction clears matrices
  (=image.c:2381-2416=, =xdisp.c:18192=). Keep live strip images below ~40.
- pgtk HiDPI: surfaces carry the device scale; Emacs draws logical pixels;
  SVG is rasterized at device size then scaled 1/f (=image.c:3072-3076=).
  Raster strips: render at width × =frame-scale-factor=, display at logical size.
- Emacs master (32) adds =canvas= images ([[https://github.com/emacs-mirror/emacs/commit/d5f515e4a3350079330c2e80f3681d140d649c88][d5f515e]], 2026-08-16, bug#80281):
  ARGB32 pixel buffers refreshed in place with =canvas-refresh=, redrawing only
  glyphs showing the image. Not present in the user's build b157d8e9
  (verified: =(image-type-available-p 'canvas)= ⇒ nil). Planned fast path.
- =read-process-output-max= is 65536 on 31/32 (verified live).

** Existing Emacs readers
- pdf-tools 1.3.0: epdfinfo (poppler/cairo) writes PNG (level 1, no filter) to
  a temp file (=epdfinfo.c:751-866=); HiDPI renders 2× and displays with
  =:width=. Roll mode renders whole pages synchronously inside
  =pre-redisplay-functions= (=pdf-roll.el:194-238=); issues #344/#345/#373.
- emacs-reader ([[https://codeberg.org/MonadicSheep/emacs-reader][codeberg]], 4fca3aa): dynamic module, 8 threads with cloned
  contexts, whole-page PPM via =create-image … 'pbm t=, ±5 page cache, one
  overlay per page; a canvas port branch exists. No document lock around
  =fz_load_page= across threads was found (unconfirmed race).
- DocView pre-renders every page with external converters.
- EAF pdf-viewer uses PyMuPDF/Qt outside Emacs' display engine.
- doc-tools ([[https://github.com/dalanicolai/doc-tools][dalanicolai]], main a9c1b0f, 2023-02; dev 2026-05): =mutool draw=
  renders every page to PNG files under =/tmp/doc-tools/= when a file opens,
  then an image-roll display engine scrolls them; page count, sizes and text
  come from poppler's command-line tools.  Its MuPDF backend loads its author's
  own paths (=/home/dalanicolai/git/…=); its dev branch hard-codes one book's
  page directory.  Not packaged; the README calls it a work in development.
- pdf-tools with the vimura server (same author: fork branch =production=
  6808471, 2022-05, and vimura-server 1.3 on PyPI, 2022-05-02): an
  interactive =python -q= with PyMuPDF answering epdfinfo's requests, found
  through Python's user site; it logs at DEBUG level into =~=.  Its precursor
  vimura-epc is marked deprecated, "a very simple basic proof of concept".
- etaf-reader ([[https://github.com/emacs-taf/etaf-reader][emacs-taf]], created 2026-10-12): a text ebook reader; a PDF
  becomes poppler's =pdftotext= text in a SQLite library, so no page is drawn.
- Not working viewers: epdf ([[https://github.com/zbelial/epdf][zbelial]], 2021) is Emacs's module-test
  skeleton (=mod-test-sum=); yapdf ([[https://github.com/condy0919/pdf-mode][condy0919/pdf-mode]], 2021) embeds a GTK
  widget but =yapdf-new= never passes its FILE on.  appine (2026) embeds macOS's
  PDFKit (Objective-C), so it cannot run on Linux.

implementations are goals, not established facts. Record evidence and
